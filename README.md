# Ломбард: залог и выкуп

Тестовое задание — два экрана внутренней системы ломбарда: оформление залога и выкуп с расчётом процентов по тарифу.

Стек: NestJS + TypeORM + PostgreSQL, React + TypeScript (Vite, Ant Design).

## Запуск

Понадобятся Node.js 20+ и Docker.

```bash
docker compose up -d

cd server
npm install
npm run seed        # тарифы и группы товаров
npm run start:dev   # API на http://localhost:3000

cd ../client
npm install
npm run dev         # UI на http://localhost:5173
```

Postgres слушает порт 5433, чтобы не пересекаться с локальным. Настройки подключения можно переопределить через `server/.env` (образец — `.env.example`), по умолчанию всё совпадает с docker-compose.

Клиентов в сиде нет — они создаются кнопкой «Новый клиент» прямо из формы залога.

## Тесты

```bash
cd server
npm test            # юнит-тесты калькулятора процентов
npm run test:e2e    # интеграционные, через реальный API
```

E2e-тесты ходят в реальные эндпоинты через supertest с отдельной базой `lombard_test` — она создаётся автоматически в том же контейнере. Покрыто:

- выкуп в срок, с просрочкой и ровно в дату «до»;
- повторный выкуп — 409, сумма первого выкупа не перетирается;
- пять параллельных запросов на выкуп одного залога — проходит ровно один;
- разные тарифы дают разные суммы при одинаковом займе;
- выкупленный залог исчезает из списка активных;
- создание залога: сумма и дата «до» считаются сервером, валидация сумм и товаров, 404 на несуществующие тариф/клиента/группу;
- поиск клиентов не ломается спецсимволами `%` и `_`.

Чтобы даты в тестах были детерминированными, залоги создаются напрямую в БД со сдвинутой датой «до» относительно текущего дня, а сам выкуп идёт через API.

## Решения по неоднозначным местам

**Формула просрочки.** В ТЗ она оставлена открытой, я взял подневную схему: `overdueRate` — процент от суммы займа за каждый календарный день просрочки. Итого при просрочке:

```
сумма выкупа = займ + займ × basePeriodRate / 100 + займ × overdueRate / 100 × дни_просрочки
```

Проценты за основной период начисляются полностью независимо от того, на какой день просрочки пришёл клиент. Помесячную схему (процент за каждый начатый период) делать не стал — в ТЗ пример расчёта дан именно через количество дней.

**`overduePeriodDays`.** Трактую как срок, в течение которого залог ещё можно выкупить после даты «до» (дальше имущество уходит на реализацию — это вне рамок теста). Поле хранится в тарифе и показывается в условиях, но в расчёте не участвует; `NULL` означает открытый период («далее»).

**Граница периода.** Выкуп ровно в дату «до» — ещё основной период, просрочки нет. Дни просрочки = `сегодня − дата «до»`, только если разница положительная. Даты хранятся как `date` без времени, разница считается по календарным дням через UTC-полночь, чтобы не ловить сдвиги на таймзонах.

**Деньги и округление.** В БД суммы лежат как `numeric(12,2)`, весь расчёт идёт в копейках целыми числами, проценты округляются до копейки арифметически. Float-арифметики в расчёте нет.

**Единая точка расчёта.** Формула живёт только на бэкенде (`server/src/pledges/redemption-calculator.ts`). Фронт показывает расшифровку с `GET /api/pledges/:id/redemption`, а `POST /api/pledges/:id/redeem` тем же калькулятором фиксирует итоговую сумму и дату выкупа. Повторный и параллельный выкуп отсекаются транзакцией с блокировкой строки — второй запрос получает 409.

**Сумма займа** считается на сервере как сумма оценочных стоимостей товаров, клиентскому значению не доверяем. На стоимость одного товара стоит верхняя планка 100 млн, чтобы не упереться в переполнение `numeric(12,2)`.

**Характеристики товаров.** Набор полей группы хранится в БД (`item_categories.fields`, jsonb) и отдаётся через API — форма строится по этой схеме динамически, новые группы добавляются без правок фронта. Значения лежат в `pledge_items.attributes` (jsonb).

## Что не успел и как бы доделал

- Схема БД создаётся через `synchronize` — для продакшена заменил бы на миграции TypeORM.
- Нет пагинации списков и проверки уникальности клиента по паспорту/телефону.
- Частичное гашение процентов и продление залога не делал — по ТЗ только полный выкуп.
- Авторизации нет (по ТЗ не требуется), guard'ы в NestJS добавляются без перестройки.
- UI собран на Ant Design без кастомизации; печать залогового билета и чеков — вне рамок.
